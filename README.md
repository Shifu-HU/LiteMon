## Features

### Main window (Task Manager-style layout)
- **Top status chips**: CPU usage + speed (GHz) / GPU usage / VRAM usage / RAM usage + used/total
- **Navigation**: CPU / GPU / RAM / DISK1 / DISK2… (USB drives appear automatically) / gear button on the right for Settings

| Tab | Content |
|---|---|
| **CPU** | Usage / speed (GHz) / temperature / power / process count summary cards + **per-core horizontal bars** (fill left to right, orange above 60%, red above 85%) + **app list** (app+PID / CPU% / memory / GPU%, sorted by CPU) |
| **GPU** | Usage / VRAM / temperature / power / core clock (GHz) + VRAM usage bar + **top GPU app** (GPU% / dedicated VRAM / shared VRAM / memory) |
| **RAM** | Usage / used/total / committed / network speed + physical memory bar + **top memory app** |
| **DISK1** | All internal drives: capacity progress bar / free space / read-write speed |
| **DISK2 / DISK3…** | **Tabs for external drives appear when plugged in and disappear when unplugged** (listed right after DISK1) |
| **⚙ Settings** | Refresh rate (0.5/1/2/5 s), autostart, theme (dark/light/follow system), 9 color schemes (three-way circle picker), **language dropdown (7 languages)**, pause, tray residency |

### Languages / 语言 / 言語
The settings-page language dropdown ships with **7 languages**: 简体中文, English, 日本語, Français, Русский, Español, العربية
(all 6 official UN languages + Japanese). Switching takes effect immediately and **stays on the current page**;
Arabic automatically switches to an RTL mirrored layout.
Adding a language only requires a new dictionary in `Services/Loc.cs` (keys aligned with `Zh`) registered in `Loc.Available`.

### External drive detection (why your portable drive shows up)

Windows **often reports USB drives as internal** — not a LiteMon bug, it's legacy baggage at the OS level:

| Case | DriveInfo reports | PNPDeviceID | MediaType |
|---|---|---|---|
| USB flash drive / some portable drives | `Removable` | `USBSTOR\...` | Removable Media |
| **Drive enclosure (USB-bridged SATA/NVMe)** | ⚠️ **`Fixed`** | ⚠️ `SCSI\...` | ✅ `External hard disk media` |
| Empty card-reader slot | `Removable` (0 capacity, not ready) | `USBSTOR\...` | — |
| Internal NVMe / SATA | `Fixed` | `SCSI\...` | Fixed hard disk media |

The middle row is the trap: **the bridge chip in a drive enclosure (JMicron / RTL9210 / ASMedia etc.) presents the drive over the SCSI channel**,
so Windows' `DriveInfo.DriveType` returns `Fixed` and `PNPDeviceID` doesn't start with `USBSTOR` —
relying on only these two fields misclassifies portable drives as internal (and no DISK2 tab appears).

LiteMon therefore **checks three fields**, and treats the drive as external if any matches:

```
PNPDeviceID starts with USBSTOR / USB    → flash drives, some portable drives
InterfaceType contains USB               → same as above, another phrasing
MediaType contains External              → ★ the only reliable signal for USB-bridged enclosures
MediaType contains Removable             → card readers / removable media
```

The logic is extracted into a pure function `DiskCollector.IsExternalBus(pnp, iface, media)` — **no WMI dependency, unit-testable on any machine and in CI**
(see `tests/LiteMon.Core.Tests/SmokeTests.cs`, covering all four real-world device strings above).
If your device is still misdetected, please open an issue with the output of:

```powershell
Get-CimInstance Win32_DiskDrive | Select-Object Model, InterfaceType, MediaType, PNPDeviceID
```

Also, **empty card-reader slots with 0 capacity and no readiness never generate a tab** (no phantom empty DISK2).

> On "Active Time": Task Manager's disk activity percentage comes from `% Idle Time`. On many platforms that counter
> keeps returning 0 for long periods (including this project's dev machine), which would display Active Time as a
> permanent 100% — **more misleading than useful**, so LiteMon doesn't show it. Read/write speeds use an independent,
> reliable pipeline and are unaffected.

### Collection & fallback chains (never crashes)
| Data | Primary source | Fallback 1 | Fallback 2 | When all unavailable |
|---|---|---|---|---|
| CPU total/per-core usage | PDH English counters `Processor Information(*)` | PDH `Processor(*)` | — | Shows 0 |
| CPU frequency | LHb clock sensor | Nominal freq × `% Processor Performance` | — | N/A |
| CPU temp/power | LibreHardwareMonitor (needs admin) | — | — | N/A (hint shown) |
| Memory | GlobalMemoryStatusEx | — | — | — |
| GPU usage/VRAM/temp/power/clock | **NVML** (official NVIDIA, no admin needed) | LibreHardwareMonitor | PDH GPU counters (VRAM only) | "No GPU detected" mask |
| Network speed | PDH `Network Interface(*)` summed (loopback/virtual excluded) | — | — | Shows 0 |
| Per-app CPU/memory | `Process` API (two-frame delta, Task Manager methodology) | — | — | Empty list |
| Per-app GPU%/VRAM | PDH `GPU Engine` / `GPU Process Memory` summed per pid | — | — | 0 |
| Disk capacity/free | DriveInfo (GetDiskFreeSpaceEx) | — | — | Empty list |
| Disk read/write speed | PDH `LogicalDisk(X:)` English counters (`Disk Read/Write Bytes/sec`) | — | — | Shows 0 |
| Removable drive plug/unplug | Per-frame drive-letter enumeration diff (DriveInfo), Disk2+ tabs appear/vanish within 1 s | — | — | — |
| **External drive verdict** | Joint check of Win32_DiskDrive PNPDeviceID / InterfaceType / **MediaType** | — | — | Treated as internal |

Every collector runs in its own try/catch with a one-shot fallback flag: **if one pipeline breaks, only its metric is
affected — the app itself never goes down** (works fine without a discrete GPU, without drivers, without admin rights).

## Measured numbers (dev machine: Intel Core Ultra 9 275HX + RTX 5060 Laptop / 32GB / Win11)

| Metric | Measured | Target |
|---|---|---|
| CPU usage (of whole machine) | **0.13%** | < 1%~2% ✅ |
| Memory (Private Bytes) | **~102MB** | < 50MB ⚠️ |
| Memory (Working Set) | ~160MB | — |

> On memory: a 50MB target is unrealistic for the **.NET 8 + WPF** framework baseline (an empty WPF window app is
> already ~70-80MB). Optimizations done: GC heap hard limit (32MB), ListView rebuilt only every 2 s, LHb sensors
> throttled to 3 s, process enumeration throttled to 2 s. If "50MB" means **net added memory**, the actual delta of
> ~30-40MB is on target. If a hard <50MB absolute is required, a native Win32/WinUI rewrite is the path (roadmap).

### Data accuracy (compared against Task Manager)
- CPU: PDH `% Processor Time` — same source as Task Manager
- Per-app CPU: `ΔTotalProcessorTime / ΔWallTime / logical cores`, matches Task Manager (one core pegged shows ~4.2% on 24 cores)
- Per-app VRAM: `GPU Process Memory` counter — same source as Task Manager's "Dedicated GPU memory"
- GPU/VRAM/temperature: NVML = official NVIDIA precision

## Build

### Prerequisites
- Windows 10/11 x64
- [.NET 8 SDK](https://dotnet.microsoft.com/download/dotnet/8.0) (winget: `winget install Microsoft.DotNet.SDK.8`)

### One-click build
```bat
build.bat
```
Output: `src\LiteMon.Wpf\bin\Release\net8.0-windows\LiteMon.exe`

### Manual build
```bat
dotnet restore LiteMon.sln
dotnet build LiteMon.sln -c Release
dotnet test tests\LiteMon.Core.Tests\LiteMon.Core.Tests.csproj
```

### Publish single-file exe (portable, ~65MB, bundles the .NET runtime)
```bat
dotnet publish src\LiteMon.Wpf\LiteMon.Wpf.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:EnableCompressionInSingleFile=true -o publish
```
Output: `publish\LiteMon.exe` — single file, double-click to run, no .NET install needed.

### Framework-dependent build (smaller, target machine needs .NET 8)
```bat
dotnet publish src\LiteMon.Wpf\LiteMon.Wpf.csproj -c Release -r win-x64 --self-contained false -o publish-lite
```

## Design notes (why it's fast)

1. **Single collection thread**: PDH has thread-affinity constraints and a single thread needs no locks; snapshots are immutable, swapped by atomic reference, UI pulls one-way
2. **PDH English counters** (PdhAddEnglishCounter): works on non-English Windows (dodges the PerformanceCounter localization trap)
3. **NVML over LHb**: no admin needed, official precision, minimal overhead
4. **UI throttling**: app list rebuilt every 2 s, LHb sensors every 3 s, process enumeration every 2 s
5. **No third-party UI/tray libraries**: tray is hand-written Shell_NotifyIcon P/Invoke, charts are self-drawn with a 120-point ring buffer
6. **Graceful degradation**: every pipeline has its own try/catch + one-shot fallback flag — exception storms are impossible

## Stability design
- Global exception guards: UI DispatcherUnhandledException + AppDomain never crash, only log
- Failed collectors return last frame's data or 0, never throw
- Log rotation: %LOCALAPPDATA%\LiteMon\log.txt truncated at 2MB
- Settings write failures are silent (no exit on disk problems)
